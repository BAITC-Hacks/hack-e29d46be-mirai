# Протокол работы ИИ-агентов в этом репозитории

Этот файл читает каждый ИИ-агент (Claude Code, Codex и др.) перед началом работы.
Команда Mirai: 3 человека, 3 активных агента (+ Claude в резерве), кейс **«Граф денег»** на хакатоне HackAlem AI.
Агенты общаются **только через GitHub** (issues, PR, комментарии). Цель — работать параллельно
и не ломать чужую работу.

## Читать перед работой (по порядку)
1. этот файл;
2. `docs/CASE.md` — сжатое ТЗ кейса;
3. `docs/CONTRACTS.md` — схемы данных и интерфейсы между частями (**главное для параллельной работы**);
4. `docs/PLAN.md` — кто что делает и таймлайн;
   `docs/HANDOFF.md` — **текущее состояние, открытые PR, порядок мержа и что осталось** (с 15:15);
5. `data/README.md`, `starter/README.md` — данные и стартовый код от организаторов.

## Правило №0: сначала спроси
- **Перед началом работы** задай своему человеку уточняющие вопросы: что неясно в задаче, какие есть
  варианты решения, что он предпочитает. Не пиши код, пока не получил ответы на ключевые вопросы.
  Обязательные стартовые вопросы — в твоём промпте (`docs/PROMPTS.md`).
- **По ходу работы**: если неоднозначность влияет на результат или есть несколько разумных вариантов —
  предложи 2–3 варианта с рекомендацией и спроси. Не угадывай молча.
- **Вопрос к другому агенту** — не угадывай, как устроена чужая часть: задай вопрос в issue
  с меткой `for:<имя>` (см. ниже) и продолжай работу на моке.
- Люди вайбкодят: объясняй простыми словами, что сделал и как это проверить.

## Золотые правила
1. **Никогда не пушь в `main` напрямую.** Только через PR.
2. **Никогда не делай `force-push`, `reset --hard`, `rebase` чужих веток.** Свою — можно.
3. **Не редактируй файлы вне своей зоны.** Нужно изменение — issue владельцу.
4. **Не мержи PR** — мержит только человек (squash merge).
5. **Никогда не коммить секреты.** Ключи только в `.env` (он в `.gitignore`).
6. **Одна задача = один issue = одна ветка = один PR.** PR маленькие, мержим часто.
7. Застрял на 15 минут — остановись, метка `blocked` на issue, скажи своему человеку.

## Рабочий цикл

### 0. Перед началом любой работы
```bash
git checkout main && git pull --ff-only
gh issue list --state open
gh pr list --state open
gh issue list --label "for:<твоё-имя>"     # запросы и вопросы к тебе
```

### 1. Взять задачу
```bash
gh issue edit <N> --add-assignee @me --add-label "in-progress"
gh issue comment <N> --body "[agent:<имя>] Беру. План: ..."
```
Если issue назначен на другого — **не трогай**. Нет подходящего issue — создай его в своей зоне.

### 2. Ветка
```bash
git checkout -b <префикс>/<N>-<кратко>      # напр. nurai/7-node-search
```

### 3. Работа
- Коммиты понятные: `feat(app): поиск по gid (#7)`.
- Регулярно подтягивай main: `git fetch origin && git rebase origin/main`.
- Пушь ветку часто: `git push -u origin HEAD`.
- Перед PR проверь, что `python run.py` не сломан (когда он уже есть).

### 4. PR
```bash
gh pr create --title "feat(app): поиск по gid (#7)" --body "Closes #7

## Что сделано
## Как проверить
## Затронутые общие файлы / контракты
нет"
```
Скажи своему человеку, что PR готов. Мержит человек.

## Общение между агентами
Все сообщения — в issue/PR с префиксом `[agent:<имя>]`.

**Запрос или вопрос другому агенту:**
```bash
gh issue create --title "[request] <что нужно>" --label "for:<имя-владельца>" \
  --body "[agent:<моё-имя>] Нужно / вопрос: ...
Зачем: ...
Блокирует: #<мой issue> (или 'не блокирует')
Предлагаю: ..."
```
Пока ждёшь ответа — используй мок/заглушку на своей стороне, чужой код не трогай.

**Изменение контракта:** отдельный маленький PR с меткой `contract`, в описании — что меняется и кого
затрагивает. Мерж только после 👍 всех троих людей.

**Статус:** раз в ~45 минут и в конце сессии — комментарий в своём issue:
`[agent:<имя>] Статус: сделано X, осталось Y, блокеры: Z.`

## Секреты и LLM
- `.env` — локально, не в git. Переменные — в `.env.example`.
- `LLM_PROVIDER=nvidia|openai|anthropic|none`. NVIDIA (build.nvidia.com) OpenAI-совместимый:
  `base_url=https://integrate.api.nvidia.com/v1`, ключ `NVIDIA_API_KEY`.
- Бюджет ограничен: в разработке дешёвая модель + кэш. Всё должно работать и при `LLM_PROVIDER=none`.
- Никогда не выводи ключи в логи, коммиты, issues и PR.

## Требования кейса, которые касаются всех
- Запуск для жюри одной командой: `pip install -r requirements.txt && python run.py`.
- Формулировки — гипотезы («признаки консолидации»), не обвинения.
- Не выдумывать атрибуты клиентов (имя, возраст, доход) — только структура и суммы.
- Не хардкодить gid под «правильный ответ».
