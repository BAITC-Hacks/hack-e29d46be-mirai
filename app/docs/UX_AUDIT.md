## 1. Причины текущих проблем графа

Источник: [app.js на проверенном main](https://github.com/BAITC-Hacks/hack-e29d46be-mirai/blob/00d38cade04057ad949dbe895a9b559af689382c/app/static/app.js).

| Наблюдение | Причина | Доработка в app/ |
|---|---|---|
| Связи исчезают при зуме, панорамировании и перетаскивании узлов | Строка 72: `hideEdgesOnViewport:true`; вендорная реализация учитывает и draggingEles | Отключить скрытие. Проверять наличие связей во время жеста, а не только после отпускания |
| Во время зума возможна потеря резкости | `textureOnViewport:true`: во время движения преобразуется снимок сцены | Перерисовывать геометрию, отключить этот режим и измерить нагрузку |
| На Retina снижена чёткость | Принудительное `pixelRatio:1` | Сравнить auto и ограниченный DPR, например максимум 2, на ноутбуке. Не обещать одинаковую скорость при любом DPR |
| Ручная раскладка теряется | draw() удаляет все элементы и создаёт заново из pipeline x/y; focus() вызывает draw() в режимах top/ego | Хранить позиции по gid и обновлять состав графа по разнице; изменение подсветки не должно менять координаты |
| Камера скачет | draw() делает общий fit, затем focus() снова делает fit окрестности | Один переход камеры на действие; отдельные команды «центрировать клиента» и «вместить связи» |
| Слишком мелкий, бледный первый экран | Fit охватывает большой разброс координат, рёбра тонкие и полупрозрачные | Улучшить начальную композицию и контраст, увеличить область карты, сохранить ясный счётчик показанных элементов |
| После выбора большого узла карта всё ещё мелкая | Fit всех соседей может захватывать несколько удалённых кластеров | Отдельный локальный вид окружения и кнопка полного охвата; не вырезать соседей незаметно |

Документация Cytoscape подтверждает назначение hideEdgesOnViewport, textureOnViewport и pixelRatio: [initialisation](https://js.cytoscape.org/#core/initialisation). У библиотеки эти первые два режима по умолчанию выключены. Причины связаны с настройками и жизненным циклом сцены, а не только с числом узлов.

Предлагаемая плавность: переход камеры 180–250 мс, отмена предыдущего перехода новым действием; без анимации при непосредственном drag; учитывать prefers-reduced-motion. Вращающиеся частицы на всех 3 119 рёбрах не нужны. Если показывать движение потока, то только на выбранном маршруте, по запросу пользователя, с пояснением, что это обозначение направления, а не воспроизведение транзакций.

Не выполнять пересортировку всех узлов, полный remove/add и массовую смену стилей на каждом кадре. Индексы входящих/исходящих и порядок приоритета можно подготовить один раз при загрузке. При обновлении видимости использовать стабильные ID рёбер; сейчас ID edge-i зависят от состава отфильтрованного массива.

## 2. Векторная графика и читаемость — разные задачи

Текущий граф рисуется на Canvas. Узлы и рёбра представлены геометрией, но экранный результат растровый. Настройка DPR не превращает Canvas в SVG.

| Подход | Что даёт | Цена и рекомендация |
|---|---|---|
| Исправить текущий Canvas | Чёткая перерисовка на текущем масштабе, сохранение связей, существующие события и взаимодействия | Первый шаг: меньше изменений и можно объективно сравнить результат |
| SVG-экспорт текущего исследования | Настоящий векторный файл для отчёта, презентации, печати | Полезная отдельная функция; сохранить стрелки, подписи, тему и легенду |
| Интерактивный SVG-рендерер | Настоящий векторный слой страницы | Отдельный прототип и замеры всех 2 248 узлов / 3 119 рёбер; перенос событий, drag, выделения и камеры. SVG сам по себе не гарантирует скорость |
| Другой Canvas/WebGL-движок | Возможный запас производительности | Только если измерения после исправлений показывают проблему; перед демо цена миграции велика |

Возможность SVG-экспорта существует как отдельное [расширение Cytoscape](https://github.com/kinimesi/cytoscape-svg); его совместимость с нашей вендорной версией ещё не проверялась.

При сильном отдалении любая линия становится меньше экранного пикселя, даже в SVG. Нужны минимальная экранная толщина/контраст, читаемый выбранный узел и отдельный обзор кластеров. Толщину нельзя увеличивать так, чтобы она перестала передавать сумму: сохранять различия и объяснять шкалу. Подписи всех 18-значных gid одновременно перегрузят карту; показывать выбранный узел, ближайшие важные связи, остальные — по наведению/выбору.

## 3. Подтверждённые ошибки и пробелы UX в нашей зоне

1. **Выбор отсутствующего в текущем виде кластера.** В top-100+соседи видно 1 280 узлов и 2 024 ребра. Полностью отсутствуют 40 из 91 кластера; кластер 27 имеет 15 узлов. Список предлагает их все, а подсветка не добавляет узлы. Нужно явно открыть выбранный кластер и его контекст.
2. **Пустая ego-сеть.** Клик по фону очищает selected, но оставляет mode=ego. Следующая перерисовка получает пустой центр. Разделить центр исследования и выбранный узел либо выходить из ego при очистке.
3. **Потеря малых метрик.** panels.js форматирует seed_exposure двумя знаками после запятой. У 2 156 узлов значение положительное, но меньше 0,005: интерфейс показывает 0. Нужны значащие цифры, отдельный формат долей и пояснения метрик.
4. **Непереведённые метрики/сигналы.** Использовать meta.metric_labels/flag_labels из #26 с локальными запасными подписями. Значения неизвестных полей показывать безопасно, а не падать.
5. **Почему высоко в рейтинге.** priority_why есть у всех узлов, но не показан в основной карточке. Разделить «Основание роли» и «Основание приоритета». role_score не называть вероятностью или статистической уверенностью.
6. **Потеря контекста чата.** Клик по gid из ответа автоматически переключает правую панель на карточку. История остаётся, но ответ исчезает с экрана. Добавить явный возврат к ответу, удержание позиции прокрутки и возможность закрепить чат/карточку.
7. **Один вопрос без контекста.** UI выглядит как диалог, но API передаёт только question, без выбранного gid и истории. «А кому он переводит?» не имеет гарантированного смысла. Можно в app явно добавлять выбранный gid к отправляемому вопросу и показывать это пользователю; полноценная история требует согласования с Даниалом.
8. **Нет исследования ребра.** В элементы Cytoscape не передаются исходные sum_kzt/n_tx, кроме производной толщины; на ребро нет карточки. Нужны отправитель → получатель, сумма, число переводов и действия открытия концов.
9. **Слишком мелкая типографика.** Во многих важных местах 9–11 px; панель карточки требует длинной прокрутки. Приоритет: более крупный основной текст, сворачиваемые метрики, входящие/исходящие ближе к началу, копирование полного gid.
10. **Карта ограничена по высоте.** Верхняя презентационная часть занимает значительную долю 720px экрана. Добавить компактную шапку/режим карты и сворачивание боковых панелей; три колонки сохранить как основной режим.
11. **Роли сейчас только легенда.** Сделать фильтры ролей и направлений, чипы активных фильтров, «Сбросить», показано X из Y. Чётко отличать фильтрацию от подсветки.
12. **Нет истории исследования.** «Назад к предыдущему узлу» должно восстанавливать камеру, режим и раскрытые связи. После drag — закрепление и «Вернуть исходную раскладку».
13. **Доступность.** Сохранить поиск/списки как альтернативу мыши; добавить полноценное переключение вкладок клавиатурой и различать статусы не только цветом. Проверить масштаб браузера 125–150%.
14. **Состояние данных.** API автоматически подставляет sample_graph, но UI не сообщает явно, что это демонстрационные данные. Нужен заметный источник/версия данных. Дата генерации графа и период транзакций должны быть разными подписями.
15. **Обновление нескольких файлов.** graph.json и top_nodes.csv читаются отдельно, а экспорт записывает их последовательно. Во время пересчёта возможны смешанные версии или временный 503. Нужен согласованный снимок/версия; со стороны app можно сохранять последний корректный вид и показывать, что данные обновляются.
16. **Ошибки чата.** При неудаче вопрос уже очищен из поля. Добавить повторить, понятный таймаут и отсутствие вечного индикатора.

Основные файлы: app/static/app.js, panels.js, index.html, style.css, panels.css, app/server.py. Текущие app/tests проверяют HTTP-контракт, ID и fallback, но не поведение камеры, drag, кластеров и интерфейса во время движения.

## 4. Вопросы к интеграции Мираса: проверить после завершения его работы

Это замечания к проверенному main и текущим веткам, не утверждение о финальном результате.

- **Экспорт extras.** export.py содержит фиксированный METRIC_COLS, в который не входят fast_transit_share, sync_in_days, repeated_route_count и другие новые поля. PR #26 добавляет подписи и флаги, но не весь экспорт численных extras. Проверить решение #21, затем показать данные в app.
- **Два определения быстрого транзита.** metrics.py считает долю исходящей суммы вскоре после любого входящего; extras.py сопоставляет суммы FIFO и считает долю входящей суммы, отдельно учитывая тот же день. Сейчас один fast_transit-флаг может объединять разные основания. Нужны разные названия/описания, знаменатель и источник сигнала.
- **Ограничение четвёртого колена.** В текущем graph.json три узла depth=4 имеют role=terminal. Правило допускает это при ≥3 плательщиках, тогда как extras отмечает неопределённость. Допустимость гипотезы должен подтвердить владелец методологии; UI обязан показывать ограничение рядом с ролью.
- **Вес взаимных рёбер при кластеризации.** clusters.py использует G.to_undirected(), а затем Louvain по sum_kzt. В данных 177 пар с переводами в обе стороны. Преобразование NetworkX не складывает разные атрибуты встречных рёбер: выбирается один набор. Для совокупного оборота нужна явная агрегация A→B + B→A. Это следует из [документации NetworkX](https://networkx.org/documentation/stable/reference/classes/generated/networkx.DiGraph.to_undirected.html); величина влияния на итоговые кластеры ещё не измерена.
- **Устойчивость по какому рейтингу.** _extras() вызывается до assign_priority и получает исходные nodes. #24 поддерживает priority_score, но при его отсутствии выбирает посредничество. В интерфейсе нельзя подписывать эти результаты «удаление лидеров нашего рейтинга» без проверки ranking_metric.
- **Неизвестное не равно нулю.** Если cycles_complete/repeated_routes_complete=false, отсутствие найденного паттерна не доказывает его отсутствия. Показывать предел поиска и состояние «поиск ограничен».
- **Время.** graph.json сейчас содержит агрегат за месяц, без временного ряда рёбер. Честный ползунок дней требует дополнительных данных из transactions, пересчёта показателей и понятной политики рейтинга.
- **Проверка входа.** load.sanity_check сравнивает наличие пар, но не сверяет n_tx и суммы агрегации transactions с edges. Стоит добавить проверку расхождений с допустимой точностью.
- **Запуск с --out.** run.py пишет в выбранную папку, но app.server по умолчанию читает ROOT/outputs. Нестандартный --out может показать старые данные. Стандартный запуск это не затрагивает.
- Обновить устаревшие упоминания владельца extras в CONTRACTS.md и комментариях, заполнить README/демо и пересчитать outputs после финальных merge.

- сохранение source, точных строковых gid, ограничений и проверки ссылок после merge.

## 6. Идеи, которые добавляют ценность

### A. Проверяемое объяснение на карте — приоритетная идея

Из карточки: «15 плательщиков» → подсветить именно 15 входящих связей; «получает от двух сборщиков» → выделить этих двух и стрелки; «связан с seed» → показать направленный путь с ограничением глубины.

Преимущество: жюри может проверить объяснение за несколько действий. Для простых входящих/исходящих достаточно текущего графа и app. Для точного обоснования сложного правила нужен структурированный evidence от Мираса: rule_id, фактическое значение, порог, подтверждающие gid/рёбра. Не пытаться надёжно восстановить это из строки evidence.

### B. Пошаговое раскрытие сети

Клиент → входящие / исходящие → следующее колено. Уже расставленные узлы остаются на месте, новые появляются рядом. «Ещё N связей» сообщает о свёрнутой части. Это отдельный режим исследования; полный граф остаётся доступен, а масштабирование само по себе не скрывает ветки.

В app возможно на текущих индексах соседства. Поиск пути — направленный BFS, с лимитом глубины и посещённых узлов. Путь в агрегированном графе не доказывает движение одной и той же суммы.

### C. Видимые границы знания

Узел четвёртого колена: пунктирный внешний контур и «дальше данных нет». Seed: значок неполных входящих. Рядом действие «Каких данных не хватает?» с конкретным следующим запросом.

Можно сделать в app по depth/is_seed/flags. Рейтинг проверки и полноту наблюдения показывать раздельно: неполные данные не равны низкому приоритету.

### D. Сравнение двух клиентов и закладки исследования

Выбрать A и B, сравнить роль, суммы, число связей, общих получателей; подсветить совпадения. Закладки хранят gid, режим, камеру и заметку локально, привязанные к версии графа. При смене данных отмечать устаревшие закладки.

Основная UI-часть наша; существующий инструмент Даниала common_recipients можно использовать для объяснений. Совпадение получателей само по себе не доказывает координацию.

### E. Устойчивость рейтинга — после согласования с Мирасом

Немного изменить веса/пороги и показать, кто стабильно остаётся в top-20, а у кого позиция чувствительна к предположениям. Метрики: частота попадания в top-K и диапазон ранга по заданным сценариям. Это устойчивость методики, не оценка вероятности нарушения. Нужны расчёты и описание сценариев в pipeline; в app — компактное объяснение.

### F. Раскрываемая карта кластеров

Отдельный обзор: кластер как группа с количеством клиентов, направлениями и суммами межкластерных переводов; по клику — исходные узлы. Переход сохраняет выбранного клиента и положение карты. Для граничных узлов показывать внешние связи.

Данные уже позволяют собрать такой обзор в app. Автоматическое сворачивание от одного лишь зума не делать первым шагом: пользователь должен понимать, какие элементы сгруппированы.

Циклы, повторяющиеся маршруты и устойчивость сети уже разрабатывает Мирас. Их отображение — интеграция существующей работы, а не новая уникальная алгоритмическая идея.

## 7. Порядок следующей работы Нурай

## 8. Критерии приёмки

- Весь граф: ровно 2 248 узлов и 3 119 рёбер; направления и точные gid сохраняются.
- На pan, wheel/pinch zoom, кнопках +/- и drag рёбра не исчезают ни на промежуточном кадре, ни после жеста.
- Переместить несколько узлов → выбрать другой → открыть кластер → вернуться: позиции сохраняются. Сброс раскладки существует отдельно.
- Каждая опция кластера приводит к его реальным узлам. Очистка выбора в ego не создаёт пустую сцену.
- Быстрые последовательные клики не накапливают перелёты камеры и не показывают устаревшую карточку.
- 1280×720, 1366×768, 1440×900; обычный/Retina экран; масштаб браузера 100/125/150%.
- Малые положительные метрики не становятся нулём; отсутствующие значения обозначены «нет данных», ноль остаётся нулём.
- По выбранному ребру видны оба gid, сумма и количество; путь сохраняет направление.
- Проверка производительности на целевом ноутбуке: измерить p95 времени кадра на 20-секундных жестах, паузы и время выбора узла. Цель — около 60 FPS, приемлемость более низкой частоты оценивать отдельно; скрытием связей результат не улучшать.
- Нет ассистента / provider=none / ошибка / таймаут / неизвестный gid: предсказуемый ответ и возможность продолжить исследование.
- Новый снимок graph.json не смешивается незаметно со старым top-list и карточкой.
- После завершения работы команды: чистая установка, python run.py, актуальные outputs и весь сценарий поиска → графа → карточки → вопроса → ссылки на узел.
